# 🛡️ Lilith: security check for vibecoded apps

**AI app builders often ship apps with the database open to everyone and secret keys visible to every visitor. Lilith finds those holes before launch and explains them in plain words.**

```bash
npx lilith-skill
```

Then open your project and tell your AI `/lilith`. You get one report:

```
Live database: checked (Supabase query results pasted)
🔴 Critical 1   🟠 High 1   🟡 Medium 2   ⚪ Cleanup 9

🔴 1. Your OpenAI key is visible to every visitor (S2)
What: NEXT_PUBLIC_OPENAI_KEY in src/lib/ai.ts:4 is sent to the browser.
Why it matters: anyone can copy it and spend your OpenAI budget.
Fix: move the call to a server route (I can do this), then replace the key
in the OpenAI dashboard (only you can do this).

Want me to fix the 🔴 ones now?
```

**No terminal? Using Lovable, Bolt or v0?** Paste the prompt from [PROMPT.md](PROMPT.md) into your project chat.

---

## Why this exists

- **CVE-2025-48757** (CVSS 9.3, critical): insufficient Row Level Security in apps generated by Lovable "allows remote unauthenticated attackers to read or write to arbitrary database tables of generated sites" ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-48757)). Lovable disputes the CVE, saying each customer is responsible for protecting their app's data.
- The researcher's scan "identified 303 endpoints across 170 projects (approximately 10.3% of the 1645 analyzed) with inadequate RLS settings" ([Matt Palmer, May 29, 2025](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)).
- UpGuard "found 16,326 Supabase databases exposing readable tables" out of about 300,000 domains using Supabase, and 55.8% of them held personal information. Its explanation: "Tables created programmatically through the API, which is how coding agents interact with Supabase, do not enable RLS by default" ([UpGuard, September 23, 2026](https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps)).

The code alone can't show whether your live database is open, so Lilith also gives you a read-only query to paste into the Supabase SQL Editor (or asks for your live Firebase rules).

## What you get

- 🔒 **Security first.** Leaked API keys, open Supabase/Firebase databases, endpoints with no login check, fake payment webhooks, missing rate limits.
- 🗄️ **Live database check.** One read-only query for the Supabase SQL Editor: it reads settings, never your data.
- 🗣️ **For beginners.** Every issue: what's wrong, why it matters, how to fix. In your language.
- 🧹 **Then cleanup.** Leftover logs, fake data, dead buttons, AI-look UI, filler marketing copy.
- 🔐 **Runs on your machine.** No account, no server, your code never leaves your computer.

## Install and use

```bash
npx lilith-skill
```

This finds the coding agents on your computer (Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, OpenCode, Windsurf) and puts the skill where each one looks. Run it again to update. Needs Node.js 18+; the quick scan also needs Python 3.8+ (optional: without it, the agent checks by reading).

```bash
npx lilith-skill --agent claude    # only one agent
npx lilith-skill --project         # into this project instead of your home folder
npx lilith-skill scan .            # run the quick scan yourself
npx lilith-skill uninstall         # remove it
```

Other tools that support [Agent Skills](https://agentskills.io) work too: `npx skills add Sunnik21/lilith -g`.

Say `/lilith`, or in words:

- "Check my app before launch"
- "Is my app safe?"
- "Clean up the AI slop in my landing page"
- "Help me secure my VPS"

## What it checks

| | Check | Example |
|---|---|---|
| S1 | Secret keys in code or git | `sk_live_...` in a file, `.env` committed |
| S2 | Secrets sent to the browser | `NEXT_PUBLIC_OPENAI_KEY`, OpenAI called from React |
| S3 | Database open to everyone | Supabase RLS off, Firebase `allow read, write: if true` (plus the live database check) |
| S4 | Endpoints with no login check | `/api/notes` writes without checking the user |
| S5 | Seeing other users' data | change `/invoices/41` to `/42` |
| S6 | Trusting the browser | price or `isAdmin` taken from the request |
| S7 | Fake payments | Stripe webhook without signature check |
| S8 | No limits | AI endpoint anyone can call 100,000 times |
| S9 | Unsafe HTML | `dangerouslySetInnerHTML` with user text |
| S10 | File uploads | private files in a public bucket |
| S11 | AI features | secrets in the system prompt, AI tools with too much power |
| S12 | Debug doors | `/api/seed`, `admin@admin.com` / `admin123` |
| S13 | Old packages | critical `npm audit` results |
| S14 | CORS and headers | any site can call your API as the logged-in user |
| C1–C8 | Code cleanup | logs, fake data, dead buttons, giant files |
| U1–U20 | UI and copy | eyebrow labels, fake badges, gradients, "seamless", "elevate" |
| VPS | Own server | firewall, SSH keys, closed database ports |

Details and fixes: [skills/lilith/guides](skills/lilith/guides).

## How well does it work?

Measured on a small benchmark in [bench/](bench/): three apps written the way AI tools write them (Vite + React + Supabase, Next.js + Supabase + Stripe + OpenAI, Express + Prisma + JWT). Together they have **31 planted security bugs** and **17 decoys** (things that look bad but are fine, like the Supabase anon key or `console.error` in an error handler). Each app also has a fixed version.

**The full skill** (one run per app, claude-opus-5-5 via `claude -p`, 2026-11-20, [bench/RESULTS.md](bench/RESULTS.md)):

- Found **31 of 31** planted bugs, including the ones no regex can see (users reading each other's data, prices trusted from the browser, Pro unlocked from `?success=true`).
- Flagged **0 of 17** decoys.
- **3 false alarms**, all "outdated packages" (S13), partly caused by the benchmark's empty lockfiles.
- Severity matched ours on **24 of 31**; when it differed, it usually rated one level higher.
- One run per app. Results vary between runs and models, and 31 bugs in three small apps is not the real world.

**The quick scan alone** (`lilith_scan.py`, deterministic, runs in CI):

| | Before this benchmark | Now |
|---|---|---|
| Planted bugs found | 16/31 (52%) | 27/31 (87%) |
| Leads that were real bugs | 22/28 (79%) | 36/37 (97%) |
| Decoys flagged | 3/17 | 1/17 |
| Critical/high leads on the fixed apps | 3 | 0 |

The new scanner patterns were written after looking at these apps, so "Now" is optimistic for your project. The scanner still misses: update policies that let users change their own `is_admin` or `plan` column, public storage buckets created in SQL, premium unlocked in the browser, and secrets inside AI system prompts. It also flags credentialed CORS even when the app uses no cookies. Those need reading, which is why the scan is only step one.

Run it yourself: `python3 bench/run_scanner.py` (scanner) or `python3 bench/run_agent.py` (full skill, needs the `claude` CLI, about $1.50 per run).

## Honest limits

Lilith is a careful first check, not a professional penetration test. It reads your code; it can't see settings that live only in your dashboards (it will tell you what to check there). It never says "your app is secure", only what it checked. For an app handling payments, health or other sensitive data, get a human review too.

## Contribute

Each check is a short section in a Markdown file. Found a hole AI tools keep making? Add it:

1. Add a section to the right guide in `skills/lilith/guides/` with **Spot it / Why / Fix**.
2. If a regex can find it, add a pattern to `skills/lilith/scripts/lilith_scan.py` and a case to `tests/test_scan.py`.
3. Run `python3 tests/test_scan.py` and `python3 bench/run_scanner.py` (the scanner score must not drop).
