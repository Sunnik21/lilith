Lilith is an agent skill that checks apps built with AI tools for the security holes those tools tend to leave: secret keys shipped to the browser, Supabase tables without row level security, API routes that never check who is calling, payment webhooks nobody verifies. It explains each finding in plain language and fixes the ones you approve. After security it can also clean up leftover AI code and UI.

## Install

```bash
npx lilith-skill
```

The installer finds the coding agents on your machine (Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, OpenCode, Windsurf) and copies the skill to where each one looks for skills. Run it again to update. It needs Node.js 18 or later. The quick scan also uses Python 3.8+ when it is installed; without Python the agent reads the code instead.

```bash
npx lilith-skill --agent claude    # one agent only
npx lilith-skill --project         # install into the current project
npx lilith-skill scan .            # run the quick scan yourself
npx lilith-skill uninstall
```

Other tools that support [Agent Skills](https://agentskills.io) can install it with `npx skills add Sunnik21/lilith -g`.

If you build in Lovable, Bolt or v0 and have no terminal, paste the prompt from [PROMPT.md](PROMPT.md) into the project chat instead.

## Usage

Type `/lilith` in your agent, or ask in plain words: "check my app before launch", "is my app safe?", "clean up my landing page", "help me secure my VPS".

Lilith reports first and changes nothing until you agree. A report looks like this:

```
Live database: checked (Supabase query results pasted)
🔴 Critical 1   🟠 High 1   🟡 Medium 2   ⚪ Cleanup 9

🔴 1. Your OpenAI key is visible to every visitor (S2)
What: NEXT_PUBLIC_OPENAI_KEY in src/lib/ai.ts:4 is sent to the browser.
Why it matters: anyone can copy it and spend your OpenAI budget.
Fix: move the call to a server route (I can do this), then replace the key
in the OpenAI dashboard (only you can do this).

Want me to fix the 🔴 ones now?
```

## Why

- CVE-2025-48757 (CVSS 9.3, critical): insufficient Row Level Security in apps generated by Lovable "allows remote unauthenticated attackers to read or write to arbitrary database tables of generated sites" ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-48757)). Lovable disputes the CVE, saying each customer is responsible for protecting their app's data.
- The researcher's scan "identified 303 endpoints across 170 projects (approximately 10.3% of the 1645 analyzed) with inadequate RLS settings" ([Matt Palmer, May 29, 2025](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)).
- UpGuard "found 16,326 Supabase databases exposing readable tables" out of about 300,000 domains using Supabase, and 55.8% of them held personal information. Its explanation: "Tables created programmatically through the API, which is how coding agents interact with Supabase, do not enable RLS by default" ([UpGuard, September 23, 2026](https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps)).

Code alone can't show whether a live database is open. For Supabase, Lilith gives you a read-only query to run in the SQL Editor; it reads settings, not your data. For Firebase it asks for your deployed rules.

Lilith has no account and no server. Your code goes only to the AI agent you already use.

## Checks

| ID | Check | Example |
|---|---|---|
| S1 | Secret keys in code or git | `sk_live_...` in a file, `.env` committed |
| S2 | Secrets sent to the browser | `NEXT_PUBLIC_OPENAI_KEY`, OpenAI called from React |
| S3 | Database open to everyone | Supabase RLS off, Firebase `allow read, write: if true` (plus the live database check) |
| S4 | Endpoints with no login check | `/api/notes` writes without checking the user |
| S5 | Seeing other users' data | change `/invoices/41` to `/42` |
| S6 | Trusting the browser | price or `isAdmin` taken from the request |
| S7 | Fake payments | Stripe webhook without signature check |
| S8 | No limits | AI endpoint anyone can call 100,000 times |
| S9 | Unsafe HTML | `dangerouslySetInnerHTML` with user text |
| S10 | File uploads | private files in a public bucket |
| S11 | AI features | secrets in the system prompt, AI tools with too much power |
| S12 | Debug doors | `/api/seed`, `admin@admin.com` / `admin123` |
| S13 | Old packages | critical `npm audit` results |
| S14 | CORS and headers | any site can call your API as the logged-in user |
| C1–C8 | Code cleanup | logs, fake data, dead buttons, giant files |
| U1–U20 | UI and copy | eyebrow labels, fake badges, gradients, "seamless", "elevate" |
| VPS | Own server | firewall, SSH keys, closed database ports |

Each check, with how to spot and fix it, is in [skills/lilith/guides](skills/lilith/guides).

## Accuracy

The benchmark in [bench/](bench/) has three small apps written the way AI tools write them: Vite + React + Supabase, Next.js + Supabase + Stripe + OpenAI, and Express + Prisma + JWT. Between them they hold 31 planted security bugs and 17 decoys, things that look wrong but are fine, such as the Supabase anon key or `console.error` in an error handler. Each app also has a fixed version.

Full skill, one run per app, claude-opus-5-5 via `claude -p`, 2026-11-20 ([bench/RESULTS.md](bench/RESULTS.md)):

- Found all 31 planted bugs, including the ones no regex can see: users reading each other's data, prices trusted from the browser, a paid plan unlocked from `?success=true`.
- Flagged none of the 17 decoys.
- Raised 3 false alarms, all outdated-package warnings (S13), partly because the benchmark's lockfiles are empty.
- Matched our severity on 24 of 31; when it differed, it usually rated one level higher.

That is one run per app on 31 bugs in three small apps. Results vary between runs and models.

The quick scan on its own (`lilith_scan.py`, deterministic, runs in CI):

| | Before this benchmark | Now |
|---|---|---|
| Planted bugs found | 16/31 (52%) | 27/31 (87%) |
| Leads that were real bugs | 22/28 (79%) | 36/37 (97%) |
| Decoys flagged | 3/17 | 1/17 |
| Critical/high leads on the fixed apps | 3 | 0 |

The newer scanner patterns were written after looking at these apps, so the "Now" column is optimistic for other projects. The scanner still misses update policies that let users change their own `is_admin` or `plan` column, public storage buckets created in SQL, a paid plan unlocked in the browser, and secrets inside AI system prompts. It also flags credentialed CORS when the app uses no cookies. Those cases need reading, which is why the scan is only the first step.

To reproduce: `python3 bench/run_scanner.py` for the scanner, or `python3 bench/run_agent.py` for the full skill (needs the `claude` CLI, about $1.50 per run).

## Limits

Lilith is a first check, not a penetration test. It reads your code and can't see settings that live only in your dashboards; it tells you what to check there. It never says an app is secure, only what it checked. If your app handles payments, health data or other sensitive data, get a human review as well.

## Contributing

Each check is a short section in a Markdown file. To add one:

1. Add a section to the right guide in `skills/lilith/guides/` with Spot it, Why and Fix.
2. If a regex can find it, add a pattern to `skills/lilith/scripts/lilith_scan.py` and a case to `tests/test_scan.py`.
3. Run `python3 tests/test_scan.py` and `python3 bench/run_scanner.py`. The scanner score must not drop.
